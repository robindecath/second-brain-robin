# Decathlon Technical Compliance — SIG Maturity Matrix

Use this skill to assess project compliance against Decathlon's mandatory technical standards, and to generate `tech_debt.md` for brownfield projects.

## What is the Maturity Matrix

The Decathlon SIG (Software Integrity Group) Maturity Matrix defines **mandatory technical requirements** across 6 domains. Each requirement has:

- A **Level** (1–5): The maturity target. Level 1 is baseline; Level 4–5 is advanced.
- A **BMAD Step**: When in the BMAD workflow the requirement should be validated.
- A **Constraint**: What is expected and why.

The full matrix data is split across domain-specific files in `data/`:

| Domain | Data File | Primary Agent |
|--------|-----------|---------------|
| Architecture standards | `data/architect-standards.md` | Architect (Winston) |
| Development standards | `data/developer-matrix.md` | Developer (Amelia) |
| Security standards | `data/security-matrix.md` | All agents |
| Infrastructure standards | `data/infra-matrix.md` | Architect (Winston) |
| Data & Streaming standards | `data/data-matrix.md` | Architect (Winston) |
| Testing standards | `data/tester-standards.md` | QA (Quinn) |

## When to Use This Skill

### Greenfield projects (new projects)
- **Step 03 – Architecture**: Architect validates the proposed architecture against `architect-standards.md`, `infra-matrix.md`, and `data-matrix.md`.
- **Step 04 – Implementation**: Developer validates code against `developer-matrix.md` and `security-matrix.md`.
- **Step 05 – Testing**: QA validates test coverage against `tester-standards.md`.

### Brownfield projects (existing projects) — CRITICAL
**Auto-detection rule**: If `_bmad-output/` already contains any existing artifact files (e.g., `architecture.md`, `prd.md`, stories, etc.), treat the project as **brownfield** and generate `tech_debt.md` automatically.

The architect MUST generate `_bmad-output/tech_debt.md` covering all 6 domains.

## Brownfield Detection Logic

When starting a conversation as the Architect agent:

1. Check if any files already exist in `_bmad-output/` (use the filesystem tool).
2. If **existing artifacts are found** → this is a brownfield project.
3. Immediately inform the user: *"I detected this is an existing project. I will analyze your codebase against Decathlon standards and generate a `tech_debt.md` documenting all improvements needed."*
4. Proceed with the brownfield analysis workflow below.

## Brownfield Analysis Workflow

When analyzing a brownfield project:

1. **Inventory existing tech**: List all technologies, frameworks, libraries, and infrastructure found in the project.
2. **Tech Radar audit**: Cross-reference every technology against the Decathlon Tech Radar (HOLD = blocking, TRIAL = flag).
3. **Maturity Matrix audit**: For each domain, check each requirement against the project's current state:
   - Level 1–2 requirements not met = baseline gap (must fix)
   - Level 3–4 requirements not met = improvement opportunity
   - Level 5 not met = advanced goal
4. **Generate `tech_debt.md`** using the structure defined below.

## Mandatory Rules

1. **All 6 domains must be covered** in `tech_debt.md` — never omit a domain even if no gaps are found (write "No gaps found" instead).
2. **Severity grouping is mandatory**: Blocking > High > Medium > Quick Win.
3. **Tech Radar violations are always P0** (blocking) regardless of perceived effort.
4. **Level 1-2 security gaps are always blocking** — they are baseline requirements.
5. **Include effort estimates**: S (< 1 sprint), M (1–3 sprints), L (> 3 sprints).
6. **Do not skip the Remediation Roadmap** — it is the actionable output the team needs.

## Do NOT

- Skip the brownfield detection check at conversation start
- Generate `tech_debt.md` without covering all 6 domains
- Mark a Tech Radar HOLD technology as "acceptable technical debt" — it is always blocking
- Create `tech_debt.md` for a greenfield project (it only applies to brownfield)
